Mapping and ACS manual for Begotten

Revised for engine 0.10.46: Part 4 is new (the editor, lights, fog, sun, co-op rules); Appendix A uses the new monster and item names. Parts 1 to 3 (the ACS reference) are unchanged.

This is the reference for the scripting language you can use in your maps. Begotten runs maps in Doom in Hexen format, whose scripts are written in ACS (Action Code Script) in its original Hexen form. That is a smaller language than the ACS of ZDoom or GZDoom, so most pages you find online describe things that do not work here.

Everything in this manual was checked against the actual engine: each example was compiled with acc -h, passed through the checker, and where it makes sense it was run in the game. Each function carries a label:

  • Works compiled and ran in the engine without errors.
  • Not fully tested or Needs ... works only under conditions, explained on the entry. "Ran without error" means just that: I could not see the result with my own eyes in the headless test, so check the visible effect in your own map.
  • Broken in this build crashes or hangs the engine. Don't use it. Version 0.1.0 had a few of these; see Appendix C.

Where to read more. ZDoom's own wiki (zdoom.org/wiki/ACS and zdoom.org/wiki/Action_specials) is the best general resource and explains the line specials in depth, but it documents the full ZDoom language. Treat this manual as the list of what is actually available here, and the wiki as extra detail about the line-special functions.

How to find things. Use the search box at the top left. Part 1 is the language itself, Part 2 the built-in functions, Part 3 the line-special functions (doors, floors, lights, things...). Part 3 is large because every special that a line in the map can have can also be called from a script by name. The appendices hold the value tables, the list of what does not work, and the checker.

Part 1 · The language

Getting started

An ACS script is a small program that lives inside a map. The map editor compiles your script text into a BEHAVIOR lump, and the engine runs it while you play. Scripts can open doors, spawn monsters, change textures and lights, and react to things happening in the map.

Compile with the -h switch. The engine understands the original Hexen script format. Modern editors compile for ZDoom by default, and the result is rejected (or worse, silently uses instructions the engine does not have). In the ACC compiler settings of your editor add -h to the command-line parameters, or compile by hand:

acc -h mymap.acs mymap.o

Put this on the first line of every script file. It gives you the constants used in this manual (SIDE_FRONT, GAME_SINGLE_PLAYER ...) and the line-special function names:

#include "zcommon.acs"

Always run the checker. acs_check.py (supplied with this manual) reads a compiled script or a whole WAD and tells you about anything the engine cannot run, before you hit it in play. This matters because acc -h happily compiles many functions that only exist in ZDoom. The engine then stops with an error such as invalid ACS instruction 196 at the moment that line runs.

python3 acs_check.py begotten.wad

Scripts and how they start

A script has a number (1 to 999), a type and optional parameters.

  • script 1 OPEN starts by itself when the map starts.
  • script 2 (void) and script 3 (int a, int b) (no type) only start when something asks for them: a line in the map with the Script Execute special (80), or another script calling ACS_Execute. A script can have at most 3 parameters.

In the map editor, a line that starts a script uses the special Script Execute: argument 1 is the script number, argument 2 is the map number (0 = this map), arguments 3 to 5 are the values for the parameters.

Only plain scripts and OPEN scripts work. ZDoom's other types (ENTER, DEATH, RESPAWN, DISCONNECT, UNLOADING, LIGHTNING...) compile but the engine treats them all like OPEN: they would run at map start instead of when the event happens. The checker warns about them.

The activator. A script started from a line has an activator, the player who crossed or used the line. Functions like Teleport, ThrustThing, HealThing and LineSide act on that activator. An OPEN script has no activator, so those functions do nothing, or even crash the game (Teleport does). Put such calls in a script started by a line.

A script ends when it reaches its closing brace, or earlier with terminate. restart starts it over from the top, and suspend pauses it for good.

Example
script 1 OPEN
{
    int i = 0;
    while (i < 3)
    {
        Delay(10);
        i++;
    }

}

Variables

All values are whole numbers (int). There are three kinds of variable:

Kind Where it is declared How many Lives
Script variable inside a script 10 per script, parameters included until the script ends
Map variable outside every script 32 until you leave the map; shared by all scripts
World variable outside every script, world int N:name; 64 (numbers 0 to 63) kept when you move to the next map

Limits of this engine:

  • A map variable cannot have a start value in its declaration (int count = 5; is a compile error with -h). Declare it, then set it in a script.
  • Write world variables as world int 3:name; (the number comes before the colon). global int does not exist here.
  • No arrays, no functions, no string variables, no decimals (fixed point). A string can only be written directly as an argument, for instance Print(s:"hello").
Example
int kills;               // map variable
world int 0:deaths;     // world variable, number 0


script 1 OPEN
{
    int tries = 3;         // script variable
    kills = kills + 1;
    deaths++;
    tries -= 1;

}

Operators

Group Operators
Arithmetic + - * / % (remainder)
Comparison == != < > <= >=
Logic && \|\| !
Bitwise & \| ^ (xor) << >>
Assignment = += -= *= /= %= ++ --

Verified in the engine: all of the above. Not available: the bitwise NOT ~, and the compound bitwise assignments &= |= ^= <<= >>= compile but stop the game when they run. Write them out in full: x = x & 3; instead of x &= 3;.

Example
script 1 OPEN
{
    int a = 7;
    int b = 3;
    int r = (a * b) % 5;      // 21 % 5 = 1
    int f = (a > b) && (b != 0);
    int m = (a & 6) | 1;      // 7 & 6 = 6, then 6 | 1 = 7
    r = r + 1;

}

Control flow

if (cond) { ... } else { ... }
while (cond) { ... }
do { ... } while (cond);
for (init; cond; step) { ... }
switch (value) { case 1: ... break; default: ... }
break;  continue;
terminate;  suspend;  restart;

All of these were run in the engine. Remember that a loop which never calls Delay runs to completion in a single game tic; an endless loop with no Delay freezes the game. Always put a Delay in loops that wait for something.

Example
script 1 OPEN
{
    int i;
    int total = 0;
    for (i = 1; i <= 10; i++)
    {
        if (i == 3) continue;
        if (i == 8) break;
        total += i;
    }
    switch (total)
    {
        case 0:
            break;
        default:
            Print(d:total);
            break;
    }

}
Example
script 1 OPEN
{
    int n = 0;
    do
    {
        n++;
        Delay(5);
    } while (n < 3);

}

Strings and messages

A string is text in double quotes. In this engine strings can only be used directly in a function call (Print(s:"hi"), ChangeFloor(1, "FLAT")): you cannot store one in a variable, compare strings or join them. See Print in the function list for what can go into a message.

Limits and what is not available

Limits

  • 3 parameters per script, 10 script variables, 32 map variables, 64 world variables.
  • Random(min, max) never returns more than 255.
  • Script numbers 1 to 999.

ZDoom features that do not work. The ACS compiler accepts all of them under -h, but the engine does not know them, so the game stops with an error when the line runs (acs_check.py finds them for you):

  • user functions (function int name()), arrays, named scripts (script "name")
  • the ZDoom file format (ACSe): the engine refuses to load the map
  • inventory (GiveInventory, CheckInventory...), actor properties (GetActorX, SetActorPosition...), HudMessage, Log, ConsoleCommand, SetMusic, PlayerHealth, Spawn, FixedMul, the x: b: f: n: l: k: parts of Print...
  • ~ and the compound bitwise assignments

The full list of such function names is in Appendix D.

Part 2 · Built-in functions

These are the functions of the language itself (as opposed to line specials). Of the 139 built-in functions that the ACS compiler knows, only the 21 below plus Print/PrintBold exist in this engine.

AmbientSound Works

AmbientSound(str soundName, int volume)

Plays a sound everywhere on the map. The sound is named by its sound-table name; volume is 0-127.

Example
script 1 OPEN
{
    AmbientSound("dsdoropn", 127);
}

Ran without crashing with audio on. A sound that does not exist is ignored. I could not listen to it in the headless test, so check by ear. Name: the sound-table name with or without the ds prefix, e.g. "dsdoropn" or "doropn"; sounds that you add to your WAD must be in the sound table. (Crashed in engine version 0.1.0; fixed in 0.1.1.)

ChangeCeiling Works

ChangeCeiling(int tag, str flatName)

Changes the ceiling texture (flat) of every sector with the given tag.

Example
script 1 OPEN
{
    ChangeCeiling(1, "CEIL3_5");
}

Verified with a flat that exists. An unknown flat name stops the game with an error.

ChangeFloor Works

ChangeFloor(int tag, str flatName)

Changes the floor texture (flat) of every sector with the given tag. The flat name is a string, in quotes.

Example
script 1 OPEN

}

Verified with a flat that exists. If the flat does not exist in your WAD the game stops with an error, so check the spelling.

ClearLineSpecial Not fully tested

ClearLineSpecial()

Removes the special from the line that started this script. Only meaningful in a script that was started by a line (walk-over, use or shoot) in the map.

Not tested, because it needs a line that triggers the script.

Delay Works

Delay(int tics)

Pauses the current script for the given number of game tics (the game runs at 35 tics per second). Other scripts and the game keep running; only this script waits.

Example
script 1 OPEN
{
    Print(s:"Get ready...");
    Delay(35 * 3);   // wait three seconds
    Print(s:"Go!");
}

Verified: Delay(35) lasted 1.0 s and Delay(105) 3.0 s.

GameSkill Works

int GameSkill()

Returns the difficulty: 0 = I'm Too Young To Die, 1 = Hey, Not Too Rough, 2 = Hurt Me Plenty, 3 = Ultra-Violence, 4 = Nightmare (constants SKILL_VERY_EASY ... SKILL_VERY_HARD).

Example
script 1 OPEN
{
    if (GameSkill() >= 3)
    {
        Thing_Spawn(50, 3, 0);   // a baron on the hard skills
    }
}

Verified. Note that the engine's -skill 3 (command line) corresponds to the value 2 returned here (the command line counts from 1).

GameType Works

int GameType()

Returns what kind of game is running: GAME_SINGLE_PLAYER (0), GAME_NET_COOPERATIVE (1) or GAME_NET_DEATHMATCH (2).

Example
script 1 OPEN
{
    if (GameType() == GAME_SINGLE_PLAYER)
    {
        Print(s:"Playing alone");
    }
}

Verified for single player. The constants come from zcommon.acs.

LineSide Works

int LineSide()

Returns which side of the triggering line the activator was on: SIDE_FRONT (0) or SIDE_BACK (1). Only meaningful in a script that was started by a line.

Example
script 1 OPEN
{
    if (LineSide() == SIDE_FRONT)
        Print(s:"From the front");
}

Ran without error from an OPEN script (value not meaningful there); not tested with a real trigger line.

PlayerCount Works

int PlayerCount()

Returns the number of players in the game (always 1 in single player).

Example
script 1 OPEN
{
    if (PlayerCount() > 1)
    {
        Print(s:"Co-op game");
    }
}

Verified for single player.

Random Works

int Random(int min, int max)

Returns a random whole number between min and max, both included.

Example
script 1 OPEN
{
    int roll = Random(1, 6);
    if (roll == 6) Print(s:"Lucky!");
}

Verified over hundreds of calls. Values are limited to 0-255 in practice: the engine draws one byte of randomness, so Random(0, 1000) never returns more than 255.

ScriptWait Works

ScriptWait(int script)

Pauses this script until another script has finished.

Example
script 2 (void)
{
    Delay(70);
}

script 1 OPEN
{
    ACS_Execute(2, 0, 0, 0, 0);   // start script 2
    ScriptWait(2);                  // wait until it is done
    Print(s:"Script 2 finished");
}

Verified. A script that ends itself with terminate wakes the waiting script up correctly (verified). See the caution under ACS_Terminate before stopping scripts from outside.

SectorSound Works

SectorSound(str soundName, int volume)

Plays a sound from the sector of the line that started the script.

Example
script 1 OPEN
{
    SectorSound("dsdoropn", 127);   // use in a script started by a line
}

Does nothing in an OPEN script (no triggering line). Plays from the sector of the line in a line-triggered script, which I could not test. (Crashed in version 0.1.0.)

SetLineBlocking Works

SetLineBlocking(int lineTag, int blocking)

Turns the "impassable" flag on or off for the lines with this tag: BLOCK_NOTHING (0) makes it passable, BLOCK_CREATURES (1) makes it block. Good for invisible walls that disappear.

Example
script 1 OPEN
{
    SetLineBlocking(10, BLOCK_NOTHING);   // open the way
}

Ran without error. Not checked visually. For finer control (monsters only, players only...) use Line_SetBlocking.

SetLineSpecial Works

SetLineSpecial(int lineTag, int special, int arg1, int arg2, int arg3, int arg4, int arg5)

Gives the lines with this tag a new line special and arguments (the same numbers you would type in the line dialog of the editor). Set the special to 0 to turn the line off.

Example
script 1 OPEN
{
    SetLineSpecial(10, 0, 0, 0, 0, 0, 0);   // disable line 10
}

Ran without error. Not checked in play.

SetLineTexture Works

SetLineTexture(int lineTag, int side, int position, str textureName)

Replaces the wall texture on one part of the lines that have the given line tag (set the line tag in the editor). side is SIDE_FRONT (0) or SIDE_BACK (1). position is TEXTURE_TOP (0), TEXTURE_MIDDLE (1) or TEXTURE_BOTTOM (2).

Example
script 1 OPEN
{
    SetLineTexture(10, SIDE_FRONT, TEXTURE_MIDDLE, "STARTAN1");
}

Ran without error. Not checked visually.

SoundSequence Not fully tested

SoundSequence(str sequenceName)

Starts a Hexen sound sequence on the sector of the triggering line. This engine has no Doom sound sequences defined, so it has little use.

Example
script 1 OPEN
{
    SoundSequence("Door");
}

Ran without error, but there is nothing to hear.

TagWait Works

TagWait(int tag)

Intended to pause the script until all sectors with the given tag stop moving (a door that has finished opening, a lift that has arrived).

Example
script 1 OPEN
{
    Door_Open(3, 32);
    TagWait(3);   // continue when the door is fully open
    Print(s:"The door is open");
}

Verified with Door_Open and Floor_LowerByValue: the script continues once the sectors have stopped moving. (This was broken in engine version 0.1.0 and fixed in 0.1.1.) Only movers that use the sector floor/ceiling are tracked; light effects such as Light_Fade are not waited for.

ThingCount Works

int ThingCount(int type, int tid)

Intended to count the things of a type and/or with a tag.

Example
script 1 OPEN
{
    Thing_Spawn(50, 23, 0, 77);        // a stimpack, tagged 77
    Delay(5);
    if (ThingCount(0, 77) == 1)
        Print(s:"It is there");
}

Verified when counting by tag. Counting by type only (tag 0) uses the numbers of Appendix A, and does not count dead monsters; that form was not verified, and the numbers count things already in the map too. Both arguments 0 returns 0. (Fixed in engine version 0.1.1; in 0.1.0 it never counted anything.)

ThingSound(int tid, str soundName, int volume)

Example

Timer Works

int Timer()

Returns how many tics have passed since the map started (35 per second).

Example
script 1 OPEN
{
    int start = Timer();
    Delay(35);
    int elapsed = Timer() - start;   // about 35
}

Verified.

Print / PrintBold Works

Print(s:"text", d:number, c:character, i:number)

Prints a message on the screen. Print shows it like a normal game message (the same place as "Picked up a clip"); PrintBold shows it in the highlighted style. Inside the parentheses you can combine several parts, separated by commas. Each part has a letter, a colon and a value:

Part Meaning
s:"text" a string
d:value or i:value a whole number, written in decimal
c:65 the character with that code (65 is "A")
Example
script 1 OPEN
{
    int kills = 12;
    Print(s:"Monsters killed: ", d:kills, s:" of ", d:20);
}

The commands ran without error. I could not check how the message looks on screen in the test setup. Not available: x: (hex), b: (binary), f: (fixed point), n: (name), l: (localized string), k: (key binding), a: (array), and Log(), HudMessage(): these compile but stop the game when they run. Use acs_check.py to catch them.

Part 3 · Line-special functions

Every special you can give a line in the editor can also be called from a script, by its name, with the same arguments in the same order. They are listed here by topic. Each entry shows the function with its arguments; arguments in [brackets] are optional.

Reading the entries

  • Tag arguments refer to the sector tag (or thing tag, or line tag) you set in the editor.
  • Speed values are in the units listed in Appendix B: 16 is slow, 32 normal, 64 fast for doors; floors and lifts have their own scale.
  • Tics are 1/35 of a second: 35 is one second, 105 is three seconds.
  • Entries with a description and example were written by hand. The others show the editor's name and argument list only; they ran without error but I have not described them in more detail. The ZDoom wiki page Action specials explains them.
  • A few specials cannot be used at all, see Appendix E.

Everything in this part is what a mapper needs to know to use Begotten's own features from Ultimate Doom Builder (UDB): the things, the lights, the haze and the sun, the co-op rules and the music lines. 4.1 Setting up UDB

  1. Unzip Begotten-UDB-config-0.10.47.zip (any later version works the same).
  2. Copy udb/Begotten_Doom2Hexen.cfg and udb/DSDADoom_DoomUDMF.cfg into UDB's Configurations folder.
  3. Copy everything in udb/Includes into UDB's Configurations/Includes folder and overwrite the older copies.
  4. Copy udb/Scripting/Begotten_ACS.cfg into UDB's Scripting folder. This is the step that makes the script editor compile your ACS with acc -h (Hexen-compatible output, which is what the engine runs). It is the same as UDB's own ZDoom_ACS.cfg except for the -h in its parameters line, and Begotten_Doom2Hexen.cfg selects it by default. It needs nothing else: UDB's own Compilers/ZDoom folder (acc, zcommon.acs and the others) is used as it is, on Windows, Linux and macOS alike. If you would rather edit UDB's file, put -h at the start of the parameters line in Scripting/ZDoom_ACS.cfg.
  5. Restart UDB. When you create a map choose Begotten: Doom 2 (Hexen format) as the game configuration, and begotten.wad as the resource.
  6. To test a map from UDB: Preferences → Testing, set the engine to begotten.exe (or the AppImage on Linux) and add -iwad "path\to\begotten.wad" to the parameters. If the game starts on the wrong map, type the map by hand: -warp 5 starts MAP05, -skill 4 picks the difficulty.

The bundle also holds LIGHTING.md (the same lighting rules as this part, in plain text), a commented BGLIGHT_example.txt, and examples/MAP01_showcase.wad, the Gallery of Lights, a finished map with every feature in it, and the script lab built on top of it. Open it in UDB to see how a window, a fog zone or a movable light is built.

4.3 Lights

Lights brighten and tint the walls, floors, ceilings and sprites around them. They are invisible in the game; in the editor they show with a stand-in sprite. Everything works in the software renderer on every platform.

  • Stationary lights (numbers 20101 to 20108) never move. When the level starts the engine traces rays through the map and stores what each light reaches, so walls, pillars, steps and closed doors cast true shadows. During play only a lookup is left. Flicker and pulse still work.
  • Movable lights (the same number plus 100: 20201 to 20208) are worked out every frame. Use them for a light on a lift or a door, or anything that must change while you play. They cast no shadows; their light spreads from their sector through open two-sided lines.

Because stationary light is baked when the level starts, it does not follow doors and lifts: a closed door blocks a stationary light for the whole level and an open door never lets it through. A light that shines through a door, or sits on a lift, must be the movable kind.

Every light thing has five arguments in the thing dialog. A 0 means "use the definition's own value".

ArgumentMeaning
Arg 1Radius, in units of 8 (10 = radius 80, 60 = 480)
Arg 2Strength in percent (50 = half, 100 = as defined; above 100 is allowed but light never goes above full bright)

How light combines

  • Brightness falls off smoothly with distance, times strength and flicker. Surfaces facing away from a light do not receive it.
  • Overlapping lights add up (never past full bright) and their colours mix: a red and a blue light make purple where they overlap.
  • Light adds to the sector's own light level, so the darker the sector, the more a light stands out. A light cannot make a sector brighter than full bright. The sector light specials (Light_*) still work and change that base level.
  • Limits: a level holds up to 128 stationary lights; at most the 12 movable lights nearest the view are used each frame; up to 48 light definitions can be loaded. Shadow edges are slightly soft (the grid is 8 units).

Things that light themselves

You do not place these. The player carries a dim lantern. Every projectile in flight glows in its sprite's colour, explosions glow brighter and wider, a power-up lying on the floor pulses, a bullet puff or chainsaw spark flashes, and a player's gun flash lights the room in front of them. The infrared goggles give a flashlight cone along the view instead of a full-bright screen; it is a live light and does not shine through walls. All of these can be tuned in the BGLIGHT lump (4.4).

Windows and shadows from floors and ceilings

Shadows are traced in 3D, so heights matter. To build a window that lets light in, make a thin sector in the wall: its floor is the sill, its ceiling is the lintel, so the two-sided line has an opening of the window's size. Put the light in a sector on the outside, high enough to shine through (a raised terrace, or a light on a pole). The floor inside gets a patch of light, with the sill and the lintel casting their own shadow. Middle textures (glass, bars, gratings) do not block light.

Warnings

When a level is baked (the first frame after it starts) the log says how long it took and warns about likely mistakes, for example stationary light 20101 at (320, 128) is near a moving sector (sector 12, a door or lift): the baked light will not follow it - use the movable twin (20201) if this light must change. It is only a hint: a lamp that merely sits in the same big room as a door is fine. On Windows the log is begotten.log, next to begotten.exe.

Fog in parts of a level

Give some sectors a Tag in the editor (sector tag), then add sector TAG to a fog line:

fog map MAP01 color 34 40 54 density 0.0018                          # the level's own fog
fog map MAP01 sector 5 color 56 34 74 density 0.0035 scatter 0.5     # sectors tagged 5: thick and violet
fog map MAP01 sector 6 density 0                                     # sectors tagged 6: clear air
  • Sectors without a line of their own have the level's fog (or none). Up to 15 zones per level. density 0 makes a clear zone.
  • A surface is seen through the thicker of its own sector's fog and the fog the viewer stands in: a clear courtyard seen from a foggy room is hazy, but a haze stays in its room.
  • The change from one fog to another is at the sector's edge, with no blending. Put zone edges at doorways and windows.
  • Works in Doom-format and UDMF maps alike (sector tags are all it needs).

Players can switch fog off in the options menu ("Fog (Where a Level Has It)"). The sky is not fogged and the first-person weapon is not fogged. Fog costs roughly 5 to 10% of the frame rate in a view full of walls.

4.6 Sun and moon, glows and coronas

Sun and moon

A level can have one directional light that falls the same way everywhere, baked at level start with real shadows:

color sunlight 255 236 200
sun map MAP01 angle 250 elevation 50 color sunlight strength 0.9
OptionMeaningDefault
mapthe level's lump name; without it, every level that has none of its ownall levels
anglewhere the sun is, in degrees on the map: 0 east, 90 north, 180 west, 270 south45
elevationheight above the horizon, 3 (low, long shadows) to 89 (overhead)40
colora colour defined with color NAME R G Bwhite
strengthbrightness on a surface that faces it squarely0.9

How to build for it. A point is in the sun when a ray from it toward the sun gets out. A sector whose ceiling is a sky flat (F_SKY1) is open to the sun; any other ceiling stops it. Walls and pillars cast shadows. A two-sided line lets sun through only inside its opening, so a window (thin sector, floor = sill, ceiling = lintel, next to a sky sector) lights a patch of the floor. Walls facing the sun are lit, walls facing away are not, and things take the light of the floor they stand on. Ceilings are never lit. The sun adds to the sector's light level and to other lights, so a dark room with a window is a good use. Outdoor floors in the shade keep the sector's own light level.

Limits: one sun per level; it does not move; doors and lifts opening after the level starts do not change it (a door that opens will not let sun in); only real sky ceilings count (a very high ceiling does nothing); the bake grid is 8 units (coarser on very large levels).

Glows (halos)

halo SIZE on a light, missile, explosion or power-up draws a soft glow round it, as if the air near it were lit. Things and walls in front of the light hide it and it fades close up. Strip lights and ceiling spots have none by default. Players switch it in the options ("Glow Around Lights").

Coronas

corona PIXELS draws a small bright star on the light that keeps the same size on the screen at any distance, so a lamp far down a hall is still a point of light. coronafade NEAR FAR gives the distances in map units: invisible at NEAR, full at FAR (default 40 and 140). PIXELS is its radius on a 320-wide view. It is hidden by anything in front of the light. Players switch it in the options ("Coronas On Lights"). The built-in torches, lamps, candles, coloured lights and missiles have one; a light you define has none unless you say so.

Dithering (a player option)

Off by default. Setup → Compatibility → "Dither Lighting (Retro Look)" blends the steps between brightness levels with an ordered pattern, giving a gritty retro grain. It costs a little frame time. Nothing to do in the editor.

4.7 Players, checkpoints and co-op

Player starts

Place Player 1 start for single player and co-op starts for players 2 to 4 (and deathmatch starts for deathmatch). A map with only one start still works for several players: players 2 to 4 are put at the first real start when they respawn.

The checkpoint line (special 174)

Give a line special 174 (Checkpoint) and set its activation to Player walks over, once or repeatable. Hexen-format and UDMF maps only. What it does:

  • Playing alone: it writes a save named checkpoint-MAPxx (one rotating slot per map) and shows "checkpoint" on screen. Dying and pressing Use reloads the last save (quick save, autosave or checkpoint, whichever came last).
  • In any multiplayer game (split-screen too): it does not save. Instead it gives one respawn ticket to each player (difficulty 4 and 5), and the line is then used up.

Put checkpoints at the start of each hard stretch.

Marking a boss

Set the Tag of any monster to a number from 30000 to 30999. When it dies, every player in a multiplayer game on difficulty 4 or 5 gets a ticket. The Mecha, the Giant beetle and any monster defined with the boss flag count without a tag. The tag does nothing else: damage immunity and other boss behaviour stay with the monster type. Use 30001, 30002 ... for different bosses if a script needs to find them; the whole range counts. Only Hexen-format and UDMF maps carry tags.

Joining a game in progress

A player can join a running network game; they start as a spectator and choose a character. A player who joins in the middle of a level does not count for completing that level (the level table and secret class only count players who were there at the start and are still there at the end). Nothing to do in the editor, but a level should not rely on a fixed number of players being present for a script.

4.8 Music lines

The Hexen-format map has two line actions that change the music: 212 Music Change (arguments: song number, "only the activator hears it", "play once" instead of looping) and 213 Music Stop (argument: "only the activator hears it"). The song number is looked up in a lump named BGMUSIC: one line per song, NUMBER LUMPNAME, for example 3 D_DRAMA. In UDMF maps you can use Music_ChangeSong (2703) directly.

4.9 Checking your work

  • Run the game with your map wad and look at begotten.log (next to begotten.exe on Windows). Look for BGLIGHT warning lines and BGLIGHT: baked N stationary lights; a bake of a big map is still short.
  • Boss deaths print BGBOSS: a boss died (monster type N, TID N) and whether tickets were on, so you can see that a tag worked.
  • Test the co-op rules with split-screen (Multiplayer → Local splitscreen) at difficulty 4 and at difficulty 2: the ticket number shows at the top right of the face on the status bar (difficulty 4 and 5, multiplayer only).
  • Run your scripts through the checker (Appendix F) before testing: it finds ZDoom-only functions that stop the game.
  • If a light is dark where you expect light, check: is its sector's ceiling or a closed door in the way (stationary lights are baked with the map as it is at the start), is it behind a one-sided line, and is the sector light level already full bright?
